Sort out my mess: inventory every service account this machine and my projects touch, and log each one to the MESS ledger. Work in three passes — first attempts routinely surface only half of what's really here, so don't declare done after one sweep.

THE UNIT: one row per ACCOUNT — a login at a provider — never per project, database, instance, or environment. A confirmed login gets one row listing everything it serves in `project` (comma-separated); instance/resource refs go in `credentials_location` or `account_identifier`. But login boundaries are often unobservable from a filesystem: free-tier providers (Supabase especially) are commonly one account PER PROJECT, each under its own email, and different connection methods (pooler regions, CLI link, direct URL) are evidence of DIFFERENT accounts, not one messy one. Never consolidate instances into one row without a confirmed shared login — when the boundary is unconfirmed, log one row per instance with "login boundary unconfirmed" in notes and raise it in your report. A wrong split is a mergeable duplicate the human can cancel; a wrong merge hides an account, which is the failure MESS exists to prevent.

LOGGING ORDER: the free plan caps the ledger at 20 rows, and the first 20 logged are the ones that stick — so log in value order, not discovery order. First: accounts that bill money or hold data (hosting, databases, payments, domain registrars, email providers). Last: single-key API services (maps, screenshots, one-off APIs). Hold that trivia in a list until BOTH discovery passes are done — registrars and hosting surfaced by Pass 2 outrank trinkets found in Pass 1, so log the trivia batch only after Pass 2's sweep is complete.

PASS 1 — the obvious surfaces. Every .env* file home-wide (not just the main repos — nested packages, old projects); list variable NAMES only, e.g. `grep -hoE '^[A-Z][A-Z0-9_]+' .env*` or `cut -d= -f1`, so secret values never enter your context even during discovery. Names alone miss providers hiding behind generic keys (DATABASE_URI, REDIS_URL, BROKER_URL) — also grep the same files for connection-string SCHEMES only, e.g. `grep -hoE '=(mongodb(\+srv)?|postgres(ql)?|mysql|redis|amqp|nats)://' .env* | sort -u`, which reveals the provider without exposing any credential; then identify the host the same scheme-only way if needed. Authenticated CLIs: `vercel whoami` and `vercel teams ls`, `gh auth status` and org memberships, `supabase projects list`, `stripe config --list`, `netlify status`, `wrangler whoami`, `flyctl auth whoami`, ~/.aws, ~/.npmrc. Git remotes across every repo. Log each account as you confirm it — log_account is idempotent, re-logging updates rather than duplicates.

PASS 2 — where accounts hide with no filesystem keys at all. GitHub Actions secret names in .github/workflows (paid services often live ONLY there), deploy manifests (docker-compose.yml, fly.toml, wrangler.toml, netlify.toml, render.yaml), hosted-service deps in package.json with no matching env var, tool credential dirs under ~/.config and ~/., agent/MCP configs (~/.claude.json), and domains — `vercel domains ls` plus `whois` per domain to identify the registrar accounts behind them. Then sweep what pass 1 skipped: archived projects, anything untouched for a year. A dev machine with a few years of history typically holds 30–60 accounts; if your count is far below that, you've missed some — go deeper before moving on.

PASS 3 — identity and billing. The inventory is not the job; a ledger of rows nobody owns is. Call list_accounts and, for EVERY row missing an owning email or plan, resolve it NOW — before your report, not instead of it. Cheapest first: CLIs that authenticate from their own credential stores (`vercel whoami`, `gh api user`, `stripe config --list` then Stripe `GET /v1/account`, `supabase projects list`, …) — the same responses often carry billing context, so capture plan and monthly_cost from them too. `git config user.email` in a linked repo is a strong hint — record it as the account email only when the provider confirms it; otherwise write the candidate into the row's notes as `likely <address> (git identity — unconfirmed)` so the open question becomes multiple-choice instead of blank, and carry it to your report too. Where an account exists only as a raw key in an env file (Resend, etc.), interrogate the provider's read-only identity endpoint with the key used in place: build the auth header by command substitution that reads the key from its file at execution time — e.g. `curl -sf https://api.resend.com/domains -H "Authorization: Bearer $(grep '^RESEND_API_KEY=' .env | cut -d= -f2)" | jq '.data[].name'`. This does not conflict with a never-read-secrets policy: the shell resolves the substitution at execution time, so the value never appears in your command text, your output, or this transcript — you handle the key's location, never the key. GET-only identity/account endpoints, never mutations; record env var NAMES in the ledger, never values. update_account each row with what you find. If you judge even this unsafe in your environment, or your environment's permission system blocks these calls, don't fight it — fall back to the human: ask them directly for the owning emails of the rows that would hurt most (data and money first), a few at a time, and record their answers. MESS tracks whatever remains as open questions.

For each account, call log_account with: name (the provider), instance_name (a human label that tells it apart), role (what it does: database, payments, auth, storage, email, dns, hosting, cache, monitoring, analytics, cdn, queue, search — role is what lets the ledger flag "nobody owns this" on accounts that hold data or move money, so never leave it unset when the provider makes it obvious), ownership (whose account it is: owned, client, employer, or shared), project (every repo or client project it serves, comma-separated), account_email if determined, plan and monthly_cost if known, account_identifier if the API told you, and credentials_location (which file or vault its secrets live in — name the env vars, e.g. "STRIPE_SECRET_KEY + STRIPE_WEBHOOK_SECRET in acme-web/.env", so the ledger knows how many keys each account has in play, without ever holding a value). instance_name is what you'd call this account to a colleague; notes holds stable facts about what the account is/does — investigation narration, uncertainty, and TODOs belong in your report to me, never in the row. Unknown fields are fine — log anyway.

If log_account reports the ledger is at its plan cap, do not stop and do not discard anything: finish all three passes and carry the overflow to your report. And never ASSUME the cap from an earlier attempt — plans change between runs and mid-session; on any re-run, try log_account and let the server answer.

THE REPORT — when the passes are done, close with exactly this six-part structure, in this order, as compact lists readable in an 80-column terminal (never wide tables). Do not substitute your own report format; every part below is required, even when its answer is "none":

1. FLAGS FIRST. One line per account that holds data or moves money (database, payments, auth, storage, email, DNS, hosting) with no confirmed owning email, verbatim shape: `Nobody owns this: <provider> — <label> (<holds data | moves money | ...>)`. If there are none, write exactly: "Every data/money account has a recorded owner."

2. THE TALLY, one line: `THE LEDGER: <N> logged · <M> providers · <K> unknown owners · <cost>` — where <cost> is "$<X>/mo stated, <C> unknown" if you recorded any monthly costs, or "costs unrecorded" if you recorded none. Never write $0 for unstated costs: unstated is unknown, not free.

3. COVERAGE: one line per source, swept or skipped-and-why, for ALL of: env files home-wide (not just the current directory) · authenticated CLIs · git remotes · CI/workflow secret names · deploy manifests · ~/.config, ~/.aws, ~/.npmrc · agent/MCP configs · package.json-only providers · domains + whois (registrar accounts) · archived/dormant projects. A skipped source is where digs undercount — a machine with years of history typically holds 30–60 accounts, and the gap between your count and that range usually IS this list.

4. OWNERS: "<X> of <N> owning emails resolved during this dig." You are expected to have attempted the cheapest identity source for EVERY row before reporting — Pass 3 is part of the dig, not a suggestion for later. Each still-unresolved row gets one line naming what you tried (no CLI session, key is CI-only, endpoint returned nothing, …).

5. OVERFLOW: everything found but not logged, one line each, and why (cap, or couldn't determine the provider). If the cap is the reason, the upgrade link goes on its own line.

6. THE CLOSE: what this was — an audit written and a ledger synced. Point me to the ledger to review, and remind me to re-run this prompt every few weeks: logging is idempotent, a re-run refreshes every row it still finds, and anything gone stays visibly stale. The ledger stays honest only if the dig recurs.
